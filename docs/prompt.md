# 查询提示词设计

项目目标：用户提供空运主提单号，服务依据航司官网返回可核实的首发 ATD、末程 ATA、完整运输分段及来源证据，明确区分缺失、冲突、无记录和查询受阻。

运行提示词的唯一来源是 [src/runtime/prompt.ts](../src/runtime/prompt.ts)。修改以业务结果为中心，按“目标 → 查询 → 运输记录 → 证据 → 输出与结束 → 操作边界”组织。所有航司使用统一提示词，仅提单号随任务变化；通过 track-trace 定位官网，依据当前页面自主操作。工具参数和操作预算以 MCP 定义与运行配置为准。

## 职责

- 模型：自主查询官网，理解表格、航段和批次，提取原始时间与可复核引用。
- 浏览器：执行受限操作，保存页面原文和截图，返回证据标识。
- 服务：校验证据、处理冲突、计算首末时间汇总并持久化结果。

提示词不重复 JSON Schema，不要求模型生成 Schema 以外的汇总字段，也不包含某张提单的预期答案。成功标准是数据真实、归属明确、信息完整；不能以返回 `complete` 为目标补齐缺失信息。

## 本次 Case 对应的规则

| 页面情况 | 提示词要求 |
| --- | --- |
| 机场代码位于航段标题，实际时间位于下方详情 | 引用包含必要上下文的连续原文，核实同票同航段，不能在摘录中自行补写机场代码。 |
| 官网使用中文实际时间标签 | 保留中文原文，仅将结构化 label 映射为 ATD/ATA，无需切换语言重新查询。 |
| 同航班号出现在不同日期或批次 | 保留各自记录，只有官网明确关联同一航段时才合并；不能仅凭航班号和件数去重。 |
| 时间可见但其归属无法证明 | 对应字段留空并说明具体缺口，其他已核实信息继续返回。 |
| 已取得完整记录 | 核对证据后输出，避免无目的地刷新、等待和重复验证。 |

## 与当前校验器的兼容

本轮修改保持现有 JSON Schema 和校验器契约：一个时间仍只有一个 `evidenceId` 和一段 `quote`，引用必须包含航班号、起止机场代码、实际标签和原始时间。因此新版要求在字段分散时保留连续上下文，而不是假设后端已支持多段证据关联。

此前讨论的“时间引用与航段引用分开，并校验关联”和“记录具体拒绝原因”需要另行修改结果结构、证据校验与诊断；仅修改提示词无法实现。扩大引用后能通过字符串校验，也不能代替对不同批次、航班日期和时间归属的核实。

## 验收

- `npm run check` 验证类型、现有自动化测试、Schema 生成和构建兼容性。
- 真实查询需对照官网核实每个时间及其航段归属，关注 `unverified_time`、错误合并、时间误配、工具调用数和耗时。
- 自动化构建通过不代表模型必然遵循提示词；本轮未将线上 Case 宣告修复。真实查询结果和截图保留在受控运行目录，不写入提示词或提交仓库。

编写方式参考 [OpenAI Docs：Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering) 中的目标、指令和上下文组织建议。
